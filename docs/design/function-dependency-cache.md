# 잠금 파일 변경을 Function 빌더가 처리하기

빌드마다 사람이 Function 이미지를 다시 만들지 않도록, uv.lock 해시별 의존성 레이어와 앱 기반 이미지를 OCIR에 캐시합니다. 동일 잠금 파일은 캐시를 재사용하고 변경 시 Function 안에서 의존성을 설치하고 레이어를 만듭니다.

실제 Functions의 `/tmp`에서는 네이티브 확장을 로드할 수 없었습니다. 새 의존성 설치와 tar 생성은 `/tmp`에서 수행하되 테스트는 해당 레이어를 포함한 새 Function 런타임이 시작된 뒤 실행합니다. Function은 RUNTIME_REQUIRED와 검증 가능한 이미지 참조를 반환하고, Companion은 허용된 저장소·digest·잠금 해시를 검증해 해당 빌더 Function의 이미지 변경 완료를 기다린 뒤 같은 소스 빌드를 한 번 이어갑니다. 임의의 OCI 오류나 응답 소실은 자동 재실행하지 않습니다.

개발·테스트 의존성은 `/opt/companion-deps/<lock-hash>/site-packages`에, 앱 의존성은 `/app/site-packages`에 배치합니다. 다른 해시 경로를 쓰므로 이전 버전의 삭제된 패키지가 새 테스트 환경에 섞이지 않습니다. 앱 코드는 별도 레이어로 추가합니다. 캐시 키에는 잠금 파일뿐 아니라 Python/플랫폼과 기반 이미지 digest를 포함하고, 레지스트리 manifest/config의 표시를 확인합니다. 캐시는 성공한 앱 이미지와 구분합니다. 테스트를 통과해야 앱 빌드 성공으로 기록합니다.

기존 인증 Secret 재사용과 Function 소스 검증을 그대로 사용합니다. 인증 파일은 레지스트리 명령 동안만 존재하며 설치·테스트 프로세스에 전달하지 않습니다. 최초 새 빌더 코드 설치는 별도 준비가 필요하지만 의존성 변경에 따른 런타임 이미지 조립은 Function 자체에서 수행합니다. 운영 앱 배포와 검증 빌더 변경은 분리하며 실제 결과는 별도 기록합니다.

런타임 변경은 관리 API의 ACTIVE 상태만으로 끝내지 않습니다. 읽기 전용 probe가 새 잠금 해시와 aarch64 실행 환경을 확인할 때까지 최대 180초 기다린 다음 빌드를 이어갑니다. 실제 OCI 검증에서 이미지 변경 직후 이전 런타임의 응답이 돌아왔으므로, 전파 확인 없이 빌드를 재실행하면 중복 런타임 전환 요청으로 실패할 수 있습니다. probe 대기 실패나 호출 오류에서는 빌드를 자동 재실행하지 않습니다.
